# Эксплуатационные исправления — 12 ноября 2026

Область: ежедневное резервирование, контроль его свежести и read-only журнал.
Торговые стратегии, лимиты, заявки, счета и разрешения PROD не меняются.

## Установленные причины

- `maintenance` не смог создать mount namespace: отсутствовал
  `/var/backups/moex-tinvest-bot`. В коде обслуживания нет удаления этого каталога;
  кто и когда его удалил, по имеющимся журналам не установлено.
- Отдельного планового резервирования не было. Копии при обновлении кода
  не обеспечивают ежедневную защиту данных.
- Read-only проверка MTSS в sandbox: запрошено 5 лотов по 10 акций,
  `lotsExecuted=50`, статус FILL, идентичности заявки совпадают, `stages=[]`.
  Это несогласованные единицы брокерского ответа, а не отказ торгового API.
  Публичный контракт T-Invest определяет `lotsExecuted` именно в лотах:
  https://developer.tbank.ru/invest/services/orders/methods

## Что изменено

1. Существующий ежедневный `maintenance.timer` запускает обслуживание только
   после успешного `moex-tinvest-backup.service`. Расписание торговых циклов
   не меняется. Бэкап сам создаёт отсутствующий каталог с ограниченными правами.
2. SQLite копируется через Backup API с проверкой integrity, а не сырым `tar`
   работающей базы. WAL/SHM не архивируются отдельно. Изменившийся обычный файл,
   повреждённая БД, ссылки и осиротевший WAL приводят к явному отказу.
   Подключение к исходной БД — `mode=ro`. Каталог состояния доступен backup-сервису
   на запись только для необходимой SQLite координации WAL/SHM: read-only mount
   не позволяет читать даже закрытую WAL-БД без существующих sidecar. Эта ситуация
   воспроизведена тестом; содержимое исходной БД при резервировании не изменяется.
3. Полный архив публикуется после сохранения независимых control-sidecar,
   SHA256 появляется последним. Монитор не принимает отчёт, sidecar или
   незавершённый архив за полноценный свежий бэкап.
4. Очистка сохраняет минимум полных комплектов: основной архив плюс его
   control-sidecar. Три отдельных sidecar не считаются тремя точками восстановления.
5. Несогласованное количество в sandbox не делится на лотность и не заменяется
   нулём. Для узко распознанного случая журнал показывает
   `sandbox_quantity_units_mismatch`, тикер, запрошенные лоты и возвращённое
   количество. Финансовые операции обновляются независимо, связь с причиной
   не создаётся. Старые операции и доказательства не переписываются.
6. API сохраняет `lineage_degraded` и число `lineage_unconfirmed`; предупреждение
   видно в качестве данных и карточке. Успешный импорт финансовой истории не
   объявляет непроверенную связь достоверной. Другие ошибки по-прежнему дают FAIL.

## Проверка и восстановление

```bash
sudo systemctl start moex-tinvest-backup.service
sudo journalctl -u moex-tinvest-backup.service -n 30 --no-pager
sudo moex-botctl diagnose --once
```

Проверять SHA следует из каталога архива. Восстановление тестировать только
в изолированной папке: integrity каждой SQLite и наличие control-sidecar.
Запрещено автоматически заменять рабочий журнал либо переносить старые control-
допуски в рабочую систему. Бэкап — согласованный снимок каждой БД, **не единая
атомарная транзакция всех intraday-файлов**. PROD/LONG writers исключены штатными
блокировками. Полное disaster recovery с конфигами и версией кода остаётся отдельным
штатным процессом `disaster-backup`; bot.env в этот state-бэкап не входит.

Off-site копия, шифрование и независимая проверка восстановления всё ещё нужны
для защиты от потери всей виртуальной машины; локальный архив этого не решает.
