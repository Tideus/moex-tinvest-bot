## Исправления и проверки

- Геополитическая блокировка запрещает увеличение риска, но не строгое уменьшение
  существующей позиции без переворота. Денежные и брокерские ограничения остаются.
- UUID отправляемой заявки резервируется в SQLite **до** сетевого запроса.
  Тайм-аут, падение процесса, UNKNOWN и незавершённое исполнение блокируют новые заявки
  на этом счёте; другой счёт не блокируется.
- В журнале сохраняется исходный intent, даже если submit не вернул ответ.
  Нельзя изменить payload под прежним идентификатором, уменьшить накопленные fills
  или заменить окончательное состояние неокончательным.
- Повтор завершённого плана не отправляется. Остаток обязательного intraday-закрытия
  получает новый UUID только после окончательного состояния прежней заявки и нового
  брокерского снимка. Закрытие не должно увеличивать позицию или переворачивать её.
- Количество исполнения проверяется на submit, polling, lookup и после отмены.
  FILLED с нулём/неполным количеством больше не подменяется полным исполнением.
- После отменённой/отклонённой/неокончательной заявки batch останавливается.
  Последующие расчёты не используют запрошенное количество вместо фактически исполненного.
- Новый план требует снимок, **начало чтения которого** позже последней окончательной
  заявки данного счёта. Проверяются часовой пояс, будущее время и длительность чтения.
- Постоянный путь журнала задаётся обязательным `--journal`, не выводится из `--output`.
  Оба установочных cycle-скрипта используют один `${STATE_DIR}/execution/orders.sqlite3`.
- `execution/` сохраняется при `reset-history`; незавершённые записи запрещают reset,
  даже если брокерский список активных заявок пуст. Обычный backup всего STATE включает журнал.
- Пустой/повреждённый файл БД не считается инициализированным журналом.
  При наличии старых execution-артефактов запрещено молча создавать новую БД.

Тесты включают перезапуск после тайм-аута, конкурирующие reservations, изоляцию счетов,
частичное закрытие с остатком, устаревшие/неполные снимки, недопустимые fills,
геоблокировку сокращения и сохранность журнала при очистке. Моки не заменяют sandbox
проверку API, испытание на Ubuntu и проверку реального брокерского исполнения.

## Восстановление незавершённых заявок

Новая команда читает GetOrderState по request UUID и обновляет только локальный журнал.
Она не отправляет и не отменяет заявки. Ответ 404, тайм-аут, пустой GetOrders или отсутствие
истории не считаются доказательством отмены/неисполнения.

```bash
sudo -u moexbot bash -c '
set -a
source /etc/moex-tinvest-bot/bot.env
set +a
exec /opt/moex-tinvest-bot/.venv/bin/python -m moex_bot.cli sandbox-journal-reconcile \
  --accounts /opt/moex-tinvest-bot/config/accounts.json \
  --profile long \
  --journal /var/lib/moex-tinvest-bot/execution/orders.sqlite3
'
```

Команда доступна только после установки исправленной сборки. Для второго счёта заменить
`long` на `intraday`. Если остались unresolved — код возврата 2 и торговля блокируется.
При миграции существующей установки сначала сверяются исторические request UUID,
операции, позиции и статусы брокера, затем переносится состояние в журнал. Автоматический
импорт теперь доступен как quarantine candidate через `sandbox-journal-prepare`; автоматический
cutover не реализован. Старые закрытые sandbox-счета не подменяют новые ID. Нельзя обойти
проверки действующего ledger удалением артефактов или созданием
пустого журнала. Нельзя восстановить только артефакты без соответствующего execution ledger.

| Блокер | Критерий закрытия |
| --- | --- |
| Manual PROD executor реализован, но не развёрнут/не активирован | Контролируемый выпуск после root admission; автономный production цикл не включать автоматически |
| Долговечность ledger и будущие миграции | Старые два sandbox закрыты; новые профили чистые. Для будущих upgrade/restore сохранять account/request UUID, ownership и pending, проверять миграцию на копии; не переинициализировать действующий PROD ledger |
| Live risk-ограничения реализованы и unit-tested, но боевые сделки не проверялись | Первый ограниченный запуск только после точного preview/подтверждения и закрытия остальных блокеров |
| Нет независимой защиты позиции при остановке сервера | Выбранная и испытанная схема защитных приказов/аварийного выхода; учёт сессий и календаря брокера вместо одного жёсткого окна часов |
| Нет актуального подтверждения преимущества стратегии | Backtest текущей версии с комиссиями, проскальзыванием, дивидендами, историческим составом universe, benchmark и stress/OOS; убрать look-ahead и selection bias |
| Нет проверенного operational evidence текущего исполнения | Подтверждённые данные ledger и брокера, а не вручную заданные счётчики или число файлов |
| Monitoring/recovery не полностью независимы | Испытанные email fallback, внешний watchdog, dead-letter alert и восстановление бота, Kuma, relay, nginx и сертификатов на новой VM |

Пороговые значения `config/promotion_gates.json` не ослаблялись: минимум 126 OOS-сессий,
30 OOS-сделок, Sharpe ≥ 0,5, excess return ≥ 0, drawdown ≤ 15%, положительный stress,
дивиденды и survivorship-safe данные; 8 sandbox-недель, 50 сверенных заявок и 0 unresolved.
Это необходимые исследовательские критерии, но не достаточное разрешение на реальные заявки.
Старый отрицательный backtest не доказывает текущую прибыльность; зелёные API/таймеры и
успешные unit-тесты также её не доказывают.

## Порядок дальнейшего допуска

1. Закрытые старые sandbox оставить в архиве; актуальные новые ID не смешивать с ними.
2. Выпустить проверенный sandbox-релиз, сохранить backup и проверить восстановление ledger.
3. Собрать воспроизводимый backtest/evidence, привязанный к revision, config и данным.
4. Live risk/execution реализованы и mock/fault-tested; завершить испытания независимой защиты.
5. Закрыть независимую защиту и эксплуатационные проверки; повторить внешний аудит.
6. Только после закрытия всех пунктов вынести решение по ограниченному canary и запросить
   отдельное подтверждение владельца счёта. Не включать PROD автоматически после зелёных тестов.

Если новый backtest не проходит критерии, остаёмся в sandbox и перерабатываем гипотезу.
Время наблюдения и реальную рыночную проверку нельзя заменить повторным запуском тестов.
