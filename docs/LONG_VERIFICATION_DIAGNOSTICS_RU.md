# Диагностика проверки защиты LONG SANDBOX

Изменение от 18.11.2026 относится только к read-only проверке. Стратегии,
лимиты, допуски, расписание и исполнитель заявок не изменяются.

## Проблема

Раньше исключение превращалось в `UNAVAILABLE` без причины и этапа. Запись
дедуплицировалась без времени, поэтому сохранялась только первая такая ошибка.
Причину единичного сбоя 17.11.2026 в 14:35 МСК восстановить из этих данных нельзя:
следующая проверка подтвердила защиту, но это не доказывает причину предыдущего сбоя.

## Что сохраняется

В `/var/lib/moex-tinvest-bot/artifacts/long-sandbox-verification/*.json`:

- `observed_at`: время начала конкретной проверки, UTC;
- `state=UNAVAILABLE`, `environment=sandbox`, `read_only=true`;
- `failure.stage`: проверка контура, журнала, допуска, покупки, позиций,
  заявок, сохранённого подтверждения стопа или самого стопа;
- `failure.source`: `local` либо `t_invest_sandbox`;
- `failure.host`, `failure.method`: фиксированный sandbox-хост и конкретный
  разрешённый read-only метод; для локального этапа — `null`;
- `failure.category`: `http`, `tls`, `dns`, `timeout`, `connection`,
  `invalid_json`, `sqlite`, `missing_file`, `permission`, `io`, `validation`
  или `unexpected`;
- `failure.reason`: безопасная причина на русском;
- `failure.http_status`: HTTP-код, если получен корректный ответ об HTTP-ошибке.

Сырые сообщения исключений, URL, заголовки, тела ответов, токены и ID счетов
не сохраняются. Из сообщений внутренних проверок допускаются только точные
заранее перечисленные фразы, заменяемые фиксированным русским описанием.
Неизвестная причина остаётся явно неизвестной, а не превращается в «API упал».

## История и уведомления

Каждая неудачная проверка имеет отдельный неизменяемый JSON, включая время.
Повторная публикация того же результата идемпотентна. Успешные подтверждения
не перезаписываются. Старые файлы не мигрируются и не дополняются выдуманными причинами.

В stdout/journald пишется безопасный `failure`, в Telegram — этап, источник,
причина и HTTP-код. Одинаковые ошибки дедуплицируются по сочетанию этих полей
в пределах календарного дня МСК. Новая причина/этап даёт отдельное уведомление;
сохраняющаяся ошибка в следующий день снова уведомляет. Существующая маршрутизация
уведомлений не изменяется. Факт отправки и чтение пользователем — разные вещи.

`UNAVAILABLE` означает, что текущая проверка не смогла подтвердить состояние,
а не что стоп точно отсутствует. Повторять BUY или создавать второй стоп нельзя.
Ожидаемая занятость блокировки писателем остаётся `WAITING`: без запросов брокеру,
без аварийного уведомления. Ошибка с такой же вложенной причиной на другом этапе
больше не маскируется как штатное ожидание блокировки.

## Проверка

Регрессии: все пять read-only API, повторное чтение стопа при проверке защиты,
повреждённый журнал, отсутствие стопа, HTTP/DNS/TLS/timeout, защита секретов,
неизменность журнала/контрольной записи, отсутствие мутирующих методов, дедупликация
уведомлений и сохранение всех неудачных наблюдений.

```bash
python -m pytest tests/test_long_sandbox_verifier.py tests/test_long_verification_diagnostics.py
```

Полный набор проверяется на копии актуального релиза, отдельно от незавершённых
пользовательских изменений. Тестовые брокерские ответы подменены; живые заявки
и тестовые Telegram-сообщения этим прогоном не отправляются.
