# Intraday: разрывы истории и ожидаемые отмены TTL

Проверка 04.11.2026 по сессии 03.11.2026. Первоначальный разбор был read-only.
Затем пользователь разрешил автодобор и установку исправлений после полного
Windows/Linux-прогона. Стратегии, лимиты и режим PROD не меняются.

## Разрывы: установленный механизм

В отчётном архиве 111 intraday-планов. В 23 циклах все 24 бумаги получили
`contiguity` — последние три сохранённые свечи не отстоят ровно на пять минут.
Это 552 отказа «бумага × цикл», а не 552 независимых торговых сигнала.
Счётчик `quality.passed` проверяет наличие входных данных, а не пригодность
каждого окна для сигнала: поэтому значение OK не опровергает эти отказы.

Для SBER входные артефакты и SQLite согласуются: отсутствуют интервалы
10:05, 10:25, 10:55, 11:10, 11:25, 11:40, 12:35, 12:55, 15:35 МСК.
Все девять сейчас присутствуют в исторических TradeStats, OrderStats, OBStats.
Их SYSTIME в полученной истории — на 10–25 секунд позже конца интервала.
Например, 10:05:16 / 10:05:14 / 10:05:19 для Trade/Order/OBStats соответственно.
Цикл 10:05 стартовал с as_of=10:05:05.892 МСК и сохранил снова 10:00;
цикл 10:10 сохранил 10:10. Интервал 10:05 в локальную историю не попал.

В коде `AlgoPackIntradayAdapter.latest()`:

1. Загружаются дневные строки с пагинацией отдельно для трёх datasets.
2. Строки объединяются по `(secid, observed_at)` и отсекаются будущие интервалы.
3. Из всех общих интервалов возвращается **только последний** для каждой бумаги.
4. `IntradayStateStore.add()` сохраняет только возвращённые строки. Добора нет.

При задержке публикации или сборщика последующий запрос может перескочить
пятиминутку. Более ранняя строка отбрасывается, даже если она уже есть в ответе.
Один пропуск нарушает несколько следующих трёхсвечных окон. Первые окна дня
могут также включать вчерашние свечи — это отдельный стартовый разрыв.

Механизм воспроизведён тестом: 09:55 → 10:00 → 10:10 при наличии 10:05 во
втором API-ответе приводит к `contiguity`. Сырые ответы трёх реальных запросов
3 ноября не сохранены: точный порядок публикации/получения и сетевую причину
каждого исторического пропуска задним числом не доказываем. SYSTIME из истории
не подменяет локальную отметку received_at.

Спецификация: [OBStats](https://moexalgo.github.io/docs/api/get-eq-obstats/),
[официальные примеры SuperCandles](https://github.com/moexalgo/algopack-skills/blob/main/skills/algopack-supercandles/references/supercandles.md).

## Реализованный автодобор: только новые решения

- Intraday вызывает `history(..., bars_per_secid=config.history_bars)`: последние
  N общих завершённых интервалов текущей московской даты. LONG по-прежнему
  вызывает `latest()`; его фильтры не меняются. Дополнительных запросов к API
  для окна не требуется: используются уже загружаемые дневные страницы.
- Нет интерполяции, forward-fill или изменения порогов. Если хотя бы один из
  трёх datasets не содержит интервал, общая свеча не создаётся. Проверка
  непрерывности и свежести остаётся обязательной.
- В SQLite добавлена таблица `intraday_bar_receipts` с временем первого получения.
  Старые строки не удаляются/переписываются; у legacy-строк время получения
  остаётся неизвестным, не назначается задним числом. Миграция аддитивная.
- `recent(as_of=..., available_at=...)` ограничивает окно текущим днём, временем
  свечи и известным временем получения. Поздняя строка не входит в более ранний
  срез по known received_at. Legacy-строки допустимы без выдуманной provenance.
- Новый план сохраняет `market_data_received_at`, `history_policy` и точное
  `history_used` из SQLite, дополнительно к полученным API `supercandles`.
  Исторические сравнения должны брать зафиксированный вход из плана, а не
  пересчитывать прошлое по пополненной БД или сегодняшнему API.
- Запись `IntradayPlan.write` выполняется с exclusive-create. CLI отказывает
  при существующем пути до сетевого запроса и записи состояния. Старые планы
  и журналы решений не обновляются автоматически.

Автодобор сработает при очередном штатном новом цикле. Старые пропуски за
3 ноября отдельной командой не заполняются, прошлые сделки не воспроизводятся.
На одинаковом полном входе формулы сигналов и риск-ограничения прежние;
восстановленное окно может дать новый сигнал, ранее заблокированный пробелом.

## TTL: исправлено отображение результата

3 ноября X5: две лимитные заявки отменены с `status=cancelled`,
`status_detail=ttl_expired`, `filled_lots=0`. Прежний CLI возвращал exit 2
из-за любого `stopped_reason`; systemd/Kuma объявляли ожидаемую отмену сбоем.

Теперь exit 0 / INFO допускается только для intraday, если:

- последняя заявка лимитная, отмена подтверждена и есть broker_order_id;
- причина точно ttl_expired, исполнено строго 0 лотов;
- все предшествующие заявки пакета полностью исполнены;
- причина остановки пакета соответствует отмене.

Исполнитель по-прежнему останавливает пакет. Не отправляет следующую заявку,
не повторяет отменённую, не повышает цену, не возвращает попытку в дневной лимит.
Журнал и состояние отменённой заявки сохраняются. Частичное исполнение,
неподтверждённая отмена, отказ брокера, market-order и другие ошибки остаются exit 2.
Поведение LONG и PROD не изменено.

В журнале: `INFO: INTRADAY SANDBOX expected_ttl_cancelled`.
В сформированном execution-отчёте: «Штатная отмена по TTL», не красный сбой.
В `monitoring-latest.json` добавлены информационные `observations`, отдельно
от проверок `checks`. Запись не старше 10 минут отображается в Kuma у
`Timers and services`: «INTRADAY SANDBOX: штатная отмена TTL без исполнения;
не сбой API». Она не превращает настоящий DOWN службы или API в UP.
Непроверенный текст из артефакта не передаётся в Kuma.

Для применения потребуется обновление бота и копии `kuma-exporter.py`, которую
запускает observer (установщик `install-kuma-adapters.py` обслуживает отдельную
копию). Статус конкретной установки фиксируется отдельной квитанцией релиза.
