# Диагностика исследовательских пропусков и сверка LONG

Эти инструменты не торгуют, не меняют стратегии и не восстанавливают прошлые
решения по более поздним данным. Техническая исправность не подтверждает прибыльность.

## Пропуски наблюдений

`scripts/research/forward_report.py` добавляет в отдельный файл
`reports/YYYY-MM-DD.diagnostics.json` раздел `diagnostics.consumer_gaps`.
Исходный алгоритм, журнал доказательств и правило полноты отчёта не изменены.
Чтение идёт из того же проверенного SQLite snapshot, что и основной отчёт.

Для каждого сохранённого пропуска модельного входа или markout указаны тикер,
стратегия, ключ и хеш решения, целевое время и горизонт. Календарь используется
только если он был доступен на момент решения, инструмент и ссылки совпадают.

| Класс | Значение |
|---|---|
| `in_session_missing` | Весь интервал от исходной точки до конца окна наблюдения внутри одной сессии; котировка отсутствует. |
| `outside_session_window` | Всё 60-секундное окно наблюдения вне сессии по сохранённому календарю. |
| `session_boundary_window` | Окно пересекает границу сессии. |
| `cross_session_window` | Целевое окно внутри сессии, но исходная точка не в той же непрерывной сессии. |
| `cross_day_window` | Окно выходит за дату решения; не переносится на следующий день. |
| `unclassified` | Нет достаточной календарной информации или подтверждённой связи с решением. |

Это классификация окна, а не доказательство недоступности API. Поле
`causal_api_failure` остаётся `null`. Коды причин `data_missing_decisions`
перенесены из оригинального решения: среди них могут одновременно быть
торговые фильтры и ошибки данных. Их нельзя все называть причинами сетевого сбоя.
Раздел описывает сохранённые потребители; отсутствие самого события продолжает
контролироваться исходными счётчиками полноты. `INCOMPLETE` не превращается в `COMPLETE`.
Повторы по вариантам стратегий не являются независимыми сделками.

`scripts/research/source_health_history.py` отдельно группирует последовательности
неудачных проверок RSS и ISS. Неизвестный статус не означает восстановление.
Первая/последняя неудачная проверка и ближайшие успешные проверки задают лишь
границы наблюдений: длительность непрерывной недоступности не вычисляется.
Работающий ISS не закрывает последовательность отказов RSS.

## Ретроспективная сверка LONG

Офлайн-инструмент читает архив отчёта и один полный брокерский receipt LONG:

```sh
PYTHONPATH=src python scripts/research/accounting_supplement.py \
  --archive /private/moex-strategy-report.tar.gz \
  --receipt /private/long-receipt.json \
  --from 2026-11-13 --to 2026-11-27 \
  --output /private/long-accounting-supplement.json
```

Формула: капитал в конечном снимке − капитал в начальном снимке − внешние
пополнения/выводы в интервале `(начало; конец]`. BUY/SELL не считаются пополнениями.
Комиссия уже отражена в брокерском капитале и повторно не вычитается.

Обязательны одинаковая привязка sandbox-счёта, корректные даты вечерних снимков,
конечные числа, полный манифест операций с уникальными ID и покрытие всего окна.
При недостатке доказательств — `UNAVAILABLE`, P&L `null`, не ноль.
Исходные ежедневные `null` сохраняются в `original_pnl`. Новый файл создаётся
эксклюзивно и не заменяет существующий. Полные ID счетов и операций не публикуются.
Хеши входов нужны для воспроизводимости, а не являются независимой подписью брокера.

Результат относится к фактическим временам снимков, не обязательно к точной
торговой сессии. Это не доходность стратегии на новых входах и не оценка
реализованной прибыли по отдельной бумаге. Нельзя суммировать пересекающиеся окна.

## Перед допуском к PROD

Отдельно требуются положительный результат на независимом периоде после расходов,
стресс с двойными расходами, проверка реального доступного капитала и ГО,
защита ручных позиций, восстановление стопа и явное разрешение оператора.
Устранение пробелов отчётности не заменяет этих проверок.
