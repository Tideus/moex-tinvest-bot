# Исправления отчётности 19 ноября 2026

Изменения не затрагивают стратегии, риск-лимиты, допуски, заявки и защитные стопы.
PROD остаётся выключенным. Замороженный исследовательский bundle и его registry
не изменяются. Прошлые решения не пересоздаются.

## Комиссии и журнал

Для двух операций T 18 ноября read-only запрос брокеру подтвердил явный ответ
`{"currency":"","units":"0","nano":0}`. Это числовой ноль, а не отсутствие
поля. Теперь дневные отчёты и веб-журнал используют общий строгий парсер:

- явный ноль с пустой валютой принимается;
- отсутствующее, нечисловое, дробное units/nano, неверные знаки и диапазоны,
  иностранная валюта либо ненулевая сумма с пустой валютой остаются неизвестными;
- неизвестная комиссия не превращается в ноль: показываются gross и «net н/д»;
- изменение капитала по брокерским снимкам известно независимо от комиссий,
  но не доказывает точный net отдельной бумаги;
- уточнение комиссии поступает новой версией наблюдения. Старые события и их
  контрольные суммы не переписываются.

## Ночной исследовательский отчёт

Старый генератор дважды проходил всю растущую hash-chain. При CPUQuota=25%
две ночные проверки были прерваны systemd по TimeoutStartSec=90s.

Новый report-only wrapper вызывает исходную реализацию замороженного отчёта.
Все запросы выполняются в одном read-only SQLite snapshot. Полная проверка
цепочки выполняется один раз на этот снимок, без долговременного кэша и без
пропуска старых записей. Разрешена только добавочная запись результата отчёта;
запись сигналов, котировок или нового registry запрещена. Последующие отчёты
заново проверяют всю историю.

Изоляция CPU/RAM сохранена; только у отчёта увеличен предел выполнения до
10 минут. В systemd выводится короткая сводка вместо мегабайтного JSON.
Полный JSON и Markdown остаются в каталоге `reports`.

На двух одинаковых приватных копиях 136 931 события зафиксирована эквивалентность
отчётов за 18 ноября, кроме времени генерации: 17,866 с → 9,294 с в тестовой среде
без service CPUQuota. Это не гарантированное время будущих запусков.

## Мониторинг и установка

`data:research-report` отдельно показывает таймаут, сбой генерации, отсутствие
свежего ночного результата, выключенный таймер и неполные наблюдения.
Код 3 означает: отчёт сформирован, но frozen-протокол выявил недостаток данных;
это не падение API и не успешная полнота эксперимента. Допускается 15 минут от
23:57 МСК на завершение. Пропуски прошлого дня остаются видимыми, а не выдумываются.

`update.sh` условно устанавливает report-only helper, только если отдельный
исследовательский сервис и проверенный bundle уже существуют. Торговые таймеры
этот helper не запускает. RSS Мосбиржи и ISS-наблюдатель остаются независимыми
проверками: успешный ISS не скрывает таймаут RSS.

Регрессии проверяют неизвестные комиссии, явный sandbox-ноль, новую версию
журнала без перезаписи, повреждение hash-chain, конкурентное добавление записей,
неизменность snapshot и различение incomplete/timeout/stale в мониторинге.

## Дополнительный таймаут сборщика веб-журнала

После установки обнаружены повторные остановки отдельного journal-collector
по лимиту 180 секунд. Профиль приватной копии: 4584 файла, около 190 тысяч
повторно проверяемых версий событий; импорт занимает 59 из 89 секунд под
профилировщиком без CPUQuota. У сервиса CPUQuota=40%, поэтому полный повтор
истории вместе с API-запросами не помещался в 3 минуты.

Добавлен производный кэш успешно импортированных наборов. Ключ включает SHA
содержимого портфеля, плана и исполнения, путь, профиль, метаданные инструментов
и код обоих адаптеров. mtime/размер не являются основанием пропуска. Маркер
пишется в одной SQLite-транзакции с событиями. Ошибки, поздно появившиеся планы,
изменившиеся файлы и конфликты не пропускаются. Изменение/удаление исходных
аналитических событий инвалидирует кэш. Это не кэш журнала исполнения.

Для проверок `import_cache=false` в конфиге журнала принудительно выполняет
полный импорт. Начальная холодная сборка ограничена 10 минутами; CPU/RAM и
расписание неизменны. В журнале службы видны этапы broker_collect, artifact_import,
analytical_report, lineage, chart_prices, publish. Ошибка содержит этап и класс,
но не данные счёта. Старая опубликованная витрина сохраняется при сбое.

## Изменяемые ID брокерских операций

Для T 18 ноября в архиве оказались две пары ID при одинаковых параметрах
исполнений. Текущая полная выгрузка содержит только одну пару. Это предусмотрено
[контрактом OperationItem](https://developer.tbank.ru/invest/services/operations/methods):
ID операции может измениться. Объединение всех когда-либо встреченных ID
ошибочно удваивало закрытия и их результат.

Новые receipts коллектора подтверждают полную пагинацию, неизменность запроса,
привязку счёта, диапазон времени, уникальный состав операций и отсутствие
конфликтующих повторов. Снимок получает манифест с количеством и SHA нормализованных
операций. Только такие проверенные окна заменяют состав операций в текущей
аналитической витрине. За пределами окна история сохраняется; более узкая свежая
выгрузка не стирает старые периоды. Старые receipts без доказательства полноты
не получают этот статус задним числом.

Источник истины — состав полной выгрузки брокера, а не совпадение цены/времени.
Две одинаковые операции с разными ID, обе присутствующие в выгрузке, остаются
двумя операциями. Связь с заявками/сигналами по-прежнему требует точных
идентификаторов, она не восстанавливается догадкой. Все исходные события, ID,
версии и контрольные суммы сохраняются; таблица исполнения не затрагивается.

В блоке качества веб-журнала показаны время сверки и число прежних ID, отсутствующих
в текущих полных окнах. Они исключены из текущего расчёта, но остаются в архиве.
Это не доказательство, что каждый старый ID однозначно соответствует новому.
Неполная пагинация, повреждённый манифест, пропавшие строки или конфликт границ
блокируют обновление витрины, сохраняя прежний отчёт с его исходным временем.
Несошедшиеся остатки/неподтверждённая база расчёта теперь дают отдельный статус
`financial_degraded` в health API, даже если сам API отвечает и данные свежие.

Тесты воспроизводят смену ID и комиссии, одинаковые реальные исполнения,
неполные/пересекающиеся окна, разделение счетов, malformed-ответы, обрыв пагинации,
неизменность архива и равенство расчёта/постраничного API.

## Права Python-пакета при установке

Послепроверка выявила зависимость pip от унаследованного `umask 077`:
root мог импортировать пакет, а moexbot — нет. Обёртка резервирования передала
эту маску установщику. Для создания venv/установки Python-кода теперь используется
локальный `umask 022` в subshell; режимы env, приватных данных и исходная маска
вне блока не ослабляются. До завершения установки выполняется импорт CLI от
имени пользователя сервиса с `python -I`, без подмены через PYTHONPATH.

`prelaunch` сначала проверяет этот импорт и при сбое не выполняет проверки API:
ошибка локального пакета не должна выглядеть как отклонённый токен ALGOPACK.

Первый полный импорт после смены адаптера занял 4 мин 53 с при прежнем лимите
5 минут. Для холодной перестройки установлен ограниченный бюджет 10 минут;
CPUQuota=40%, MemoryMax=300M и период таймера сохранены. Обычные циклы используют
кэш. Лимит не делает старую витрину свежей: API продолжает проверять реальное
время публикации и брокерского снимка.
