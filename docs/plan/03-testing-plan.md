# Полный план тестирования

## 1. Принципы

- Один код стратегии для backtest, replay, shadow и live.
- В момент `t` доступны только данные, опубликованные до `t`.
- Комиссии и проскальзывание учитываются до оценки результата.
- Все проверенные параметры регистрируются.
- Тестовый holdout нельзя многократно использовать как новую обучающую выборку.
- Sandbox проверяет механику API, но не реальную доходность.

## 2. Статический контроль

- formatter и linter;
- type checking;
- secret scanning;
- dependency audit;
- SAST;
- запрет опасных логов;
- проверка Docker image;
- license audit сторонних компонентов.

## 3. Модульные тесты

### Деньги и инструменты

- Decimal-конвертация;
- округление по шагу цены;
- штуки ↔ лоты;
- изменение lot size;
- валюты;
- нулевые и отрицательные значения;
- очень большие значения;
- расчёт комиссии.

### Стратегия

- momentum и moving average;
- отсутствие look-ahead;
- фильтр ликвидности;
- ранжирование ties;
- inverse-volatility;
- сумма весов;
- недостаточная история;
- дивидендный гэп;
- исключение недоступного инструмента.

### Risk engine

- лимит позиции и сектора;
- недостаток денег;
- дневной оборот и убыток;
- stale data;
- неизвестный торговый статус;
- GeoRisk режимы;
- неизвестная заявка;
- kill switch.

### Execution

- уникальный UUID;
- повтор с тем же UUID;
- timeout после фактического принятия;
- частичное исполнение;
- отмена;
- reject;
- события не по порядку;
- дубликаты;
- восстановление после рестарта.

## 4. Property-based тесты

Инварианты:

- количество заявки всегда целое число лотов;
- цена кратна шагу;
- целевые веса не превышают лимиты;
- риск-фильтр не увеличивает цель;
- одна идемпотентная команда не создаёт две локальные заявки;
- после сверки локальная позиция равна брокерской;
- капитал не возникает из-за округления;
- последовательность повторных событий не меняет конечное состояние.

## 5. Контрактные тесты

Для MOEX, ALGOPACK и T-Invest:

- схема ответа;
- обязательные поля;
- пагинация;
- пустые страницы;
- timestamp и timezone;
- rate limits;
- authentication errors;
- обновление контрактов;
- backoff/retry;
- stream reconnect;
- heartbeat;
- неизвестные enum-значения.

Fixtures должны быть обезличены и не содержать токены или account_id.

## 6. Интеграционные тесты

- загрузка → quality gate → БД;
- закрытие свечи → стратегия → targets;
- news → GeoEvent → GeoRisk;
- targets → risk → execution plan;
- execution plan → sandbox API;
- broker event → order state → portfolio;
- restart → reconciliation;
- миграция БД → повторный запуск.

## 7. Исторический бэктест

Обязательно учитывать:

- point-in-time вселенную;
- делистинги и новые листинги;
- изменения тикеров и лотов;
- дивиденды и сплиты;
- торговый календарь;
- комиссии выбранного тарифа;
- спред;
- проскальзывание и impact;
- задержку исполнения;
- лотовую дискретность;
- неполное инвестирование;
- зависшие и частичные заявки;
- невозможность исполнения при остановке торгов.

Бенчмарки:

- IMOEX или корректный доступный аналог;
- равновзвешенная вселенная;
- buy-and-hold;
- стратегия без геофильтра;
- стратегия без ALGOPACK-фильтров.

## 8. Walk-forward и OOS

```text
Train → Validate → сдвиг окна → повтор → Final untouched test
```

Считать:

- total return и CAGR;
- volatility;
- Sharpe/Sortino;
- max drawdown;
- Calmar;
- turnover;
- комиссия, spread cost, slippage;
- число сделок;
- win/loss и expectancy;
- exposure;
- результат по годам, бумагам и режимам;
- IS-to-OOS degradation.

## 9. Защита от переобучения

- журналировать все варианты;
- ограничить сетку параметров заранее;
- предпочитать устойчивые области, а не единичный максимум;
- применить CSCV/PBO или аналогичный контроль множественных испытаний;
- отдельно показать результат базовой простой модели;
- не использовать final test для повторного выбора параметров.

## 10. Стресс-тесты стратегии

- комиссии ×2;
- проскальзывание ×2 и ×3;
- задержка на одну и две свечи;
- пропуск 5–10% сигналов;
- исключение лучшего инструмента;
- исключение лучшего года;
- параметры ±20%;
- уменьшение доступной ликвидности;
- случайный порядок исполнения одновременных заявок;
- длительное нахождение в рублях.

## 11. Геополитический replay

Для каждого исторического события хранить время первой публикации и версии документа. Проверить:

- задержку 0/15/30/60 минут;
- первичный источник недоступен;
- ложный заголовок;
- перепечатки;
- исправление документа;
- неверное сопоставление эмитента;
- противоположную рыночную реакцию;
- одновременную остановку торгов;
- отказ LLM;
- истечение события и RECOVERY.

Необходимо сравнить фильтр с вариантом без фильтра по риску и пропущенной доходности.

## 12. Event replay live-кода

Сохранённый поток проигрывается через те же обработчики, что и live. Проверить:

- детерминированность;
- дубликаты;
- события не по порядку;
- разрыв стрима;
- пропущенную свечу;
- частичное исполнение;
- timeout после исполнения;
- отмену с задержкой;
- перезапуск в каждом состоянии заявки.

## 13. Fault injection

Отказы:

- MOEX недоступен;
- ALGOPACK 401/403/429;
- T-Invest недоступен;
- stream reconnect loop;
- PostgreSQL недоступен;
- заполнен диск;
- системное время неверно;
- DNS/сеть нестабильны;
- Telegram недоступен;
- повреждена конфигурация;
- портфель расходится с брокером.

Ожидаемая реакция: запрет новых заявок, сохранение доказательств, уведомление, сверка и контролируемое восстановление.

## 14. Sandbox

Проверить:

- токен и подключение;
- создание sandbox-счёта;
- выставление/отмену/замену;
- идемпотентность;
- активные заявки;
- обработку завершения сессии;
- рестарт;
- сверку;
- kill switch;
- rate limiting.

Песочница T-Invest использует упрощённое исполнение: она не моделирует реальный impact, очередь и глубину. Результат sandbox нельзя считать доказательством доходности.

## 15. Shadow mode

Продолжительность: 4–8 недель.

- реальные данные и расписание;
- виртуальные заявки;
- сохранение исходной котировки и стакана;
- оценка потенциального fill;
- измерение spread/slippage;
- реконнекты;
- ежедневная сверка;
- часовой GeoRisk;
- отсутствие реальных ордеров.

Gate: расхождения, stale-data incidents и потенциальные издержки укладываются в заранее заданные пределы.

## 16. Ограниченный live-пилот

- отдельный небольшой счёт;
- без плеча;
- 1–3 инструмента;
- низкий лимит позиции;
- низкий дневной turnover;
- лимитные заявки;
- ручное включение;
- автоматическая остановка при расхождении;
- ежедневный отчёт оператора.

Масштабирование только после 30–50 реальных исполнений и анализа live против shadow/backtest.

## 17. Release gates

Live запрещён, если:

- есть критический дефект;
- восстановление не протестировано;
- возможны дубликаты заявки;
- нет защищённого secret store;
- OOS не выдерживает повышенные издержки;
- shadow не завершён;
- kill switch не проверен;
- оператор не проходил recovery drill.

Материал предназначен для исследования и не является индивидуальной инвестиционной рекомендацией.
