# Одноразовый LONG в Sandbox: передача счёта

Этот режим использует существующий **рабочий long sandbox-счёт**. Не IIS и не intraday.
Установка регистрирует unit-файлы, но не инициализирует журнал, не включает таймер
и не отправляет заявки. Операции ниже выполняет только уполномоченный оператор.

1. Проверьте установленный релиз, раздельные привязки long/intraday и профиль
   `daily_long_momentum_v1`. В `/etc/moex-tinvest-bot/runtime.json` должны быть
   `t_invest_environment=sandbox` и `sandbox_orders_enabled=true`.
2. Остановите **расписание** старого LONG: `sudo systemctl stop moex-tinvest-shadow.timer`.
   Дождитесь естественного завершения `moex-tinvest-shadow.service`; не прерывайте
   возможную отправку/защиту ордера. До передачи сверьте реальные позиции,
   активные/неопределённые заявки, стопы и старый журнал исполнения **этого счёта**.
   Не отменяйте чужие заявки. Если исход неопределён — не включайте режим.
   Intraday и production не останавливаются.
3. Только для первичного подключения, не при восстановлении: убедитесь, что
   нет старого enrollment, рабочей БД или `entry.claim`. Установите маркер,
   который запрещает старому long-runner выполнять даже сверку заявок:

   ```bash
   sudo install -o root -g root -m 0644 \
     /opt/moex-tinvest-bot/deploy/ubuntu/sandbox-long-once.owner.example \
     /etc/moex-tinvest-bot/sandbox-long-once.owner
   ```

4. Отдельно и однократно инициализируйте ledger. Используйте защищённую загрузку
   EnvironmentFile через systemd: секреты не выводятся и не передаются как значения
   в командной строке. Эта команда не делает брокерского запроса:

   ```bash
   sudo systemd-run --wait --pipe --collect --uid=moexbot --gid=moexbot \
     -p UMask=0077 \
     -p EnvironmentFile=/etc/moex-tinvest-bot/bot.env \
     -p 'UnsetEnvironment=T_INVEST_PROD_TOKEN T_INVEST_READONLY_TOKEN TELEGRAM_BOT_TOKEN' \
     /opt/moex-tinvest-bot/.venv/bin/python -I -B -m moex_bot.long_auto_operator \
     init-sandbox --state /var/lib/moex-tinvest-bot/long-once/sandbox.sqlite3
   ```

5. Только после проверки `WAITING` и разрешения на **реальную sandbox-операцию**:
   `sudo systemctl enable --now moex-tinvest-long-once-sandbox.timer`. Это включает
   расписание 10:05 МСК по будням, без догоняющего запуска. Прямой запуск service
   может отправить sandbox-заявку; не используйте его как smoke-test. Старый
   shadow-таймер можно вернуть в его прежнее состояние: пока маркер существует,
   его сервис пропускается до любых preflight/брокерских действий. Диагностика:
   `systemctl list-timers moex-tinvest-long-once-sandbox.timer` и
   `journalctl -u moex-tinvest-long-once-sandbox.service`. Доставка Telegram не обещана.

Каждый допустимый запуск использует собственные свежие geo, снимок long-портфеля
и risk-gated hourly-shadow с исходной стратегией. ISS/ALGOPACK, консервативное
окно сессии и брокерский статус проверяются отдельно. Инвесткалендарь остаётся
наблюдательным; его события не подменяют торговый календарь. Нет подходящего BUY —
нет заявки. Один состоявшийся claim никогда автоматически не перевооружается.

**Остановка и авария.** Отключение будущих попыток:
`sudo systemctl disable --now moex-tinvest-long-once-sandbox.timer`. Не останавливайте
работающий service посередине BUY→защита. При `QUARANTINED`, потерянном ответе
или расхождении ledger и независимого файла
`/var/lib/moex-tinvest-control/long-once-sandbox/entry.claim` прекратите запуски
и вручную сверьте родителя, исполнения и стоп у брокера. Не удаляйте маркер,
ledger или claim и не повторяйте init. Контрольный файл находится вне обычного
state/backup/reset; восстановление старой копии рабочего ledger его не обнуляет.
Обычная резервная копия сохраняет историю ledger для разбора, а не разрешение
на запуск. Backup и изменяющие LONG-команды исключают друг друга общей блокировкой;
аварийная распаковка создаёт только изолированный карантин, не рабочую БД.
Если утрачен сам хост/контрольный каталог, **не** поднимайте старую БД как новый
`WAITING`: докажите независимо историю этой попытки и согласуйте действия.
Локальный latch не защищает от администратора, стирающего оба источника.

### Что именно проверяем

Это **одна попытка на весь эксперимент**, не одна покупка в день. Выбор идёт
в порядке лимитных BUY реального утреннего плана, уже прошедших фильтры long,
ALGOPACK и риск-контроль. Если нет ни одного подходящего входа, состояние
остаётся `WAITING`. Файл со вчерашним сигналом, тикер, заданный вручную, или план
intraday использовать нельзя. Защищённые тикеры и уже имеющиеся позиции пропускаются.
Перед покупкой бот повторно сверяет инструмент, состояние рынка, стакан, доступные
деньги и стоимость с комиссией. Лимит — **один лот, не дороже 10 000 ₽ с комиссией**.

Триггер защитного стопа — 98% от лимита покупки с округлением вниз до шага цены.
Это постоянный брокерский SELL stop-loss с рыночным исполнением, не тейк-профит
и не гарантия цены. При гэпе цена исполнения может быть хуже триггера.
Стоп выставляется **после подтверждённого исполнения**, только на приобретённый лот;
между исполнением покупки и подтверждением стопа есть интервал без защиты.
Бот не продаёт другие позиции. Если лимитка не исполнена за окно наблюдения,
бот проверяет её состояние, пытается снять только собственный остаток и сверяет ответ.
Исполненная, отменённая, отклонённая и неопределённая попытки не дают права на новый вход.

| Статус журнала | Что он доказывает |
| --- | --- |
| `WAITING` | Попытка ещё не зарезервирована; это не исполненная сделка. |
| `ENTRY_NOT_FILLED` | Подтверждён терминальный исход без исполнения. Нового входа не будет. |
| `FILLED_PROTECTED` | Подтверждены покупка и активный стоп у брокера на момент сверки. Это не обещание, что стоп до сих пор активен. |
| `CLAIMED`, `ENTRY_OBSERVED`, `CANCEL_PENDING`, `STOP_PENDING`, `QUARANTINED` после остановки процесса | Не считать позицию защищённой. Проверить ордер, стопы и позицию у брокера; не отправлять повторную покупку. |

В том же окружении, что в шаге 4, замените `init-sandbox --state …` на
`status` для чтения журнала или на `reconcile` для запроса состояния родительской
заявки по сохранённому UUID. Отдельная операторская команда `recover-stop` **может
выставить только стоп в песочнице**: нужен сохранённый подтверждённый FILLED и
доказательство отсутствия предыдущей отправки стопа. Не вызывайте её вслепую.

**Отдельно от ИИС.** `python -m moex_bot.long_auto_operator prod-preview --help`
описывает построение связанного предпросмотра на основании свежего плана самого
ИИС. Сигнал sandbox нельзя перенести как приказ на ИИС. В новом таймере нет
отправки PROD-заявок; действующий механизм подтверждения конкретного BUY и
стопа на ИИС не отключается. Исполнение в песочнице и работа реального стопа
на ИИС — разные проверки.
