# Одноразовый LONG-автовход на ИИС: код и допуск оператора

## Статус

Режим добавлен как **выключенный кандидат**, не как разрешение торговать.
В этой доработке нет создания production-допуска, установки на vivek, включения
таймера или отправки реальных заявок. Intraday остаётся на отдельном sandbox-счёте.
Тесты с fake broker не заменяют сквозную проверку реальной песочницы и независимый аудит.

## Алгоритм

1. Проверить отдельный root-controlled конфиг, допуск на конкретный релиз/ИИС/журнал
   и ещё не использованную попытку. Не переключать глобальный runtime в prod.
2. В отдельном каталоге цикла получить geo, свежий снимок **ИИС**, сформировать
   торговую часть портфеля и выполнить текущую LONG-стратегию `prod_shadow.json`.
   Сигнал sandbox, intraday или произвольный файл «последний план» не используется.
3. Выбрать первый уже прошедший фильтры BUY из реального плана. Тикер заранее
   не закреплён: действует текущий allowlist, UID/класс/лот/тик проверяются отдельно.
   План связан SHA256 с конкретным снимком счёта. На входе ему менее пяти минут;
   до отправки остаётся минимум три минуты для защиты.
4. Read-only preflight: открытый ИИС, права, текущий стакан и статус торгов,
   свободные рубли, сумма с комиссией ≤10 000 ₽, отсутствие выбранной бумаги
   среди ручных позиций, отсутствие конфликтующих заявок, действующие риск-лимиты.
   Определённый отказ ДО резервирования не расходует попытку.
5. Под общей PROD-блокировкой создать независимый `claim.json`, затем сохранить
   план стопа и резервирование BUY. При отправке создать `buy-dispatch.json`
   эксклюзивно и синхронизировать на диск **до** вызова брокера.
6. Отправить лимитный BUY одного лота. Независимо перечитать его состояние.
   Проверять исполнение ограниченное время (30 опросов); при необходимости снять
   только собственный подтверждённый неисполненный остаток и перечитать результат.
7. Только после FILLED одного лота — поставить брокерский рыночный stop-loss,
   создав перед отправкой отдельный `stop-dispatch.json`. Перечитать стоп и
   подтвердить UID, сторону, объём, тип и триггер. ACK сам по себе не доказывает защиту.
8. Любой уже существующий claim запрещает новую покупку, включая после отказа,
   отмены, потери ответа, смены сигнала, перезапуска или восстановления старой БД.
   Неопределённый результат требует разбирательства; автоматических повторов нет.

Стоп — не гарантия цены/убытка. Между исполнением BUY и подтверждением стопа есть
интервал без защиты; гэп и недоступность API могут увеличить убыток. Плановая
дистанция стопа с резервом издержек дополнительно проверяется против риск-бюджета.

## Ручные бумаги и Intraday

Новый runner использует только `T_INVEST_PROD_ACCOUNT_ID`, проверяет тип ИИС и
его отличие от sandbox ID. Общие `accounts.json`/`runtime.json` не изменяются.
Выбранная бумага должна отсутствовать на ИИС перед покупкой; смешивать ботовый
лот с существующим ручным пакетом запрещено. Защита ограничена одним новым лотом.
Любое расхождение по позициям блокирует действие. Ручные заявки не отменяются.

## Подготовка оператором, без автоматического включения

Безопасная локальная проверка конфигурации (без API):

```bash
python -m moex_bot.prod_long_once_operator config-check --settings config/prod_long_once.json
```

До ручного включения необходимы:

- проверенный неизменный релиз, полный pytest, Ruff, strict mypy и Linux smoke;
- отдельный независимый аудит этой новой ветки, не только предыдущего ручного исполнителя;
- sandbox-свидетельство успешного цикла BUY → подтверждённый активный native stop;
- восстановление с сохранённым независимым claim: старая БД не разрешает новый BUY/стоп;
- свежая сверка ИИС, его ручных позиций, заявок, стопов, денег и зарегистрированного журнала;
- отдельно созданные оператором `/etc/moex-tinvest-bot/prod-long-once.json` и
  `/etc/moex-tinvest-bot/prod-long-once-admission.json`, root-owned без group/world-write;
- существующий приватный `0700` каталог `/var/lib/moex-tinvest-control/prod-long-once`
  и приватный каталог артефактов `/var/lib/moex-tinvest-bot/prod-long-once` для service user.

Допуск проверяется `validate_grant`: `decision=OPERATOR_AUTHORIZED_PROD_LONG_ONCE`,
`version=1`, SHA256 полного ID счёта (сам ID в публичных отчётах не сохраняется),
`release_sha256` из штатного `release_digest`, `journal_uuid`, фиксированные лимиты
и оба защитных флага. `reviewed_at`/`expires_at` — timezone-aware, срок ≤24 часов;
перед началом остаётся ≥5 минут. `evidence_sha256` содержит реальные SHA256 отчётов
`tests`, `independent_audit`, `restore_drill`, `sandbox_fill_and_native_stop`.
Заполнить хеши произвольными строками — не пройти аудит; root-оператор отвечает за
проверку самих свидетельств. Код не выставляет эти факты автоматически.

Шаблоны units имеют суффикс `.example`; штатные install/update их не активируют.
Оператор устанавливает их как service/timer **только после** выполнения критериев.
Плановое окно шаблона — 10:10 МСК по будням, `Persistent=false`.
Старый LONG sandbox при переходе требует отдельного решения оператора; этот код
не выключает/перепривязывает существующие аккаунты и не вмешивается в intraday.

`status` не вызывает broker API: DISABLED / ARMED_WAITING / ALREADY_CLAIMED.
ARMED_WAITING означает пригодность локального допуска, не готовность текущего
рынка и не подтверждение позиции/защиты. `run` — **торговое действие**, не smoke-test.
Запрет новых входов — выключение отдельного таймера/конфига. Не прерывать service
посередине BUY→стоп; изменение допуска во время исполнения может заблокировать защиту.

## Восстановление и мониторинг

Нельзя удалять claim/dispatch-файлы, переинициализировать журнал, подменять account ID
или возвращать старую БД, чтобы повторить вход. При потере самого контрольного
каталога нельзя воссоздавать пустой каталог как доказательство отсутствия сделки.

`recover_stop_only` — отдельная библиотечная операция для сопровождаемого
восстановления, не ветка таймера: требуется неизменный claim, сохранённый FILLED,
свежий коррелированный ответ брокера, PLANNED в журнале защиты и отсутствие
`stop-dispatch.json`. Не отправляет BUY. Если стоп уже отправлялся или исход
неизвестен — повтор запрещён даже после отката БД. Общий `production_session`
должен удерживаться вызывающим оператором на протяжении всей операции.
Универсальную legacy-команду восстановления для этой новой ветки применять нельзя.

Штатный runner публикует подтверждённый итог через существующий Telegram outbox,
а ошибки — через независимый alert relay. `ALREADY_CLAIMED` не утверждает, что
стоп всё ещё активен: для постоянного контроля нужна брокерская сверка.
Текущие серверные health/Kuma и дневной LONG-отчёт относятся к sandbox: до активации
нового PROD-режима требуется отдельно добавить его текущую защиту и P&L в мониторинг.

## Границы проверки

Новые unit-тесты: cap с комиссией, ручные позиции, строгие типы лимитов, неверный
счёт/контур, устаревший сигнал, повтор с другим сигналом, потеря ответов BUY/STOP,
восстановление пустого журнала, отдельное восстановление стопа без покупки,
откат состояния стопа при сохранённом dispatch fence, отсутствие брокерского
подтверждения, выключенный конфиг до чтения credentials, запрет sandbox/чужих методов.
Это проверка техники исполнения, не доказательство прибыльности LONG-стратегии.
