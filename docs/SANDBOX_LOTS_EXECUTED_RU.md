# Sandbox: сверка единиц исполнения (9 ноября 2026)

Наблюдение: GetSandboxOrderState вернул для GAZP `lotsRequested=8`,
`lotsExecuted=80`, статус FILL. Операции показали продажу 80 акций по 113,87 ₽,
сумма 9 109,60 ₽, позиция — минус 80 акций. При лоте 10 это 8 лотов.
До исправления строгая проверка останавливала цикл; повторной продажи не было.

## Ограниченное восстановление

Только sandbox-адаптер, только акции и полный FILL. Если lotsExecuted точно
равно заказанным лотам × размер лота и больше заказанных лотов:

1. Проверяются request UUID, broker order ID, instrument UID, сторона, количество.
2. Читаются GetSandboxOperationsByCursor на том же sandbox-счёте в узком окне.
3. Нужна ровно одна исполненная операция того же инструмента и стороны с **точным**
   временем из orderDate. Проверяются счёт, quantity/quantityDone/quantityRest,
   цена, знак денежного потока, сумма и одна подтверждающая сделка внутри операции.
4. Только после совпадения всех проверок журнал получает FILLED и исходные лоты.
   В status_detail сохраняется `sandbox_units_reconciled_with_operations`.

Sandbox в наблюдавшемся ответе не предоставил прямую связь order ID в операции,
а stages был пуст. Поэтому используется строгий составной признак, а не
сопоставление одной лишь позиции или приблизительного времени. При одинаковом
времени нескольких операций, задержке данных, пагинации, частичном исполнении
с неверными единицами или несовпадении цен восстановление **не допускается**.
Такие случаи требуют дополнительного разбора; деления на лот по умолчанию нет.

Одинаковая проверка применяется к lookup и settlement, включая readback после
TTL. При аномальном ответе PostOrder выполняется только чтение по прежнему UUID;
повторной отправки нет. Ошибка содержит тикер и этап
`order_operations_reconciliation`. Журнал остаётся незавершённым до подтверждения.

После восстановления штатный цикл заново читает портфель. Закрытие long/short
делает существующая стратегия из фактических лотов; journal reservation и
проверка свежести снимка продолжают защищать от дублирования. Стратегии, лимиты
и PROD этим исправлением не меняются.

Операции могут запаздывать: [официальная документация](https://developer.tbank.ru/invest/services/operations/head-operations).
Они используются здесь только для дополнительного подтверждения уже полученного
FILL, не вместо состояния заявки.
