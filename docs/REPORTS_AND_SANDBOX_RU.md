# Отчётность и исполнение T-Invest Sandbox

Документ описывает текущий эксплуатационный этап: акции из проверенного `universe.json`,
часовой long-контур, отдельный пятиминутный intraday-контур, явно разрешаемые заявки на двух
виртуальных Sandbox-счетах и дневной/недельный контроль результата. Production-заявки в этой
версии отсутствуют.

## 1. Режимы и границы

| Состояние | Поведение |
| --- | --- |
| `t_invest_environment=sandbox`, `sandbox_orders_enabled=false` | Чтение Sandbox-счёта, расчёт и Telegram shadow-отчёт; заявки не отправляются. |
| `t_invest_environment=sandbox`, `sandbox_orders_enabled=true` | Прошедшие risk-gate long-планы могут стать лимитными Sandbox-заявками. |
| профиль `intraday`, `order_execution_enabled=true`, `execution_stage=sandbox` | Пятиминутный runner может отправлять заявки только на `T_INVEST_SANDBOX_INTRADAY_ACCOUNT_ID`. |
| `t_invest_environment=prod` | Только чтение счёта и отчётность; production execution отсутствует. |

Часовая стратегия может открыть long и уменьшить существующую long-позицию. Intraday может
открыть long или подтверждённый Sandbox short, если T-Invest повторно сообщает доступность short
для инструмента и запрос содержит `confirmMarginTrade`. Фьючерсы и опционы пока запрещены.

## 2. Безопасное включение

```bash
sudo moex-botctl prelaunch
sudo moex-botctl sandbox-enable --confirm-sandbox
sudo moex-botctl start
sudo moex-botctl status
```

Перед записью переключателя проверяются активный контур и sandbox credentials. Следующий
успешный цикл может отправить до `sandbox_max_orders_per_cycle` заявок.

Запретить новые отправки:

```bash
sudo moex-botctl sandbox-disable
sudo moex-botctl stop
```

Первая команда не отменяет уже выставленные заявки. Перед возобновлением нужно сверить account,
positions, active orders и последний `sandbox-execution-*.json`.

## 3. Условия отправки заявки

Каждая отправка требует одновременно:

- активный контур `sandbox` и явный runtime gate;
- качественный shadow-план не старше 30 минут;
- совпадение account ID плана и execution adapter;
- отсутствие активных брокерских заявок;
- проверенный UID акции и статус плана `validated`;
- соблюдение cash reserve, позиции, gross, sector, cluster и дневного turnover;
- не более настроенного числа заявок за цикл.

Обычная входная заявка лимитная, использует UUID идемпотентности. Только intraday short явно
подтверждает margin trade. Принудительное закрытие intraday-позиции использует market-заявку;
цена последнего бара нужна для sizing и контроля, но не передаётся как лимит. При `unknown` или
`rejected` дальнейшая отправка пакета прекращается.

Перед каждым intraday-планом отдельный reconciliation получает активные заявки выделенного
счёта, отменяет их и повторно требует пустой список. Остаток после частичного исполнения
становится позицией следующего snapshot. После `force_flat_moscow` новые входы запрещены, а все
позиции закрываются; отсутствие свежей цены приводит к fail-closed ошибке.

## 4. Политика Telegram

Long shadow-отчёт отправляется только в `long.morning_analysis_hour`: качество данных, GeoRisk,
broker snapshot, целевые веса, планы и risk rejection. Вечером приходит P&L и итоговый баланс.
Остальные часовые расчёты, execution и ALGOPACK flow сохраняются без Telegram.

Intraday не отправляет сигнал, план, `accepted`, reconciliation или отмену. После каждого цикла
читаются broker operations; сообщение `INTRADAY SANDBOX · СДЕЛКА ИСПОЛНЕНА` создаётся только
для новой BUY/SELL operation и дедуплицируется по `operation_id`. Вечером приходит отдельный
итог. Полный след остаётся в JSON-артефактах, логах и `intraday.sqlite3`.

Не следует смешивать статусы:

| Статус | Значение |
| --- | --- |
| `validated` | План разрешён внутренним risk-gate, брокер его ещё не подтверждал. |
| `accepted` | Брокер принял заявку, но fill не гарантирован. |
| `partially_filled` | Исполнена только часть. Следующие пакеты блокируются до сверки. |
| `filled` | Заявка исполнена в модели Sandbox. |
| `unknown` | Неизвестно, получил ли брокер запрос; слепой retry запрещён. |

## 5. Дневной отчёт

В `schedule.daily_report_on_calendar` (по умолчанию 23:20 МСК) создаются:

```text
/var/lib/moex-tinvest-bot/artifacts/daily-performance-YYYY-MM-DD.txt
/var/lib/moex-tinvest-bot/artifacts/daily-performance-YYYY-MM-DD.json
```

Общий результат:

```text
P&L = equity в конце − equity в начале − внешние пополнения/выводы
return = P&L / equity в начале
```

Вклад бумаги оценивается как:

```text
конечная стоимость − начальная стоимость + продажи − покупки − комиссия
```

Строка `Прочее/сверка счёта` — разница общего P&L и суммы вкладов бумаг. Она может включать
непривязанные комиссии, денежные операции, округления или разницу времени снимков. Её нельзя
произвольно приписывать самой прибыльной/убыточной бумаге.

## 6. Недельный отчёт

В пятницу дневной runner дополнительно создаёт:

```text
weekly-performance-MONDAY-FRIDAY.txt
weekly-performance-MONDAY-FRIDAY.json
```

Отчёт содержит общий P&L, вклад бумаг, просадку, оборот через список операций, число циклов,
blocked/rejected, долю бумаг с положительным вкладом и сравнение с равновзвешенным universe.

Verdict — процессный gate, а не автоматическая оптимизация:

| Verdict | Действие |
| --- | --- |
| `REVIEW_DATA` | Устранить blocked/ошибки данных; стратегию не менять. |
| `COLLECT_MORE` | Операций или циклов недостаточно; продолжить OOS. |
| `REVIEW_RISK` | Проверить размеры, концентрацию и cash reserve. |
| `OBSERVE` | Отрицательная неделя; искать повторяемое OOS-ухудшение. |
| `CONTINUE_OOS` | Процесс стабилен; одной недели недостаточно для изменения параметров. |

Для разбора с Codex передаются weekly JSON, дневные JSON, соответствующие `shadow-*.json`,
`sandbox-execution-*.json` и описание известных внешних событий. Анализ должен разделять:

1. качество данных;
2. ошибку направления сигнала;
3. sizing/diversification;
4. исполнение и комиссии;
5. событие, возникшее после решения;
6. возможный заранее доступный hedge.

Изменение стратегии оформляется новой гипотезой и снова проходит replay/backtest,
walk-forward/holdout и shadow. Параметры не меняются автоматически по одной неделе.

## 7. Ограничения Sandbox

Sandbox проверяет API, состояния и эксплуатационный процесс, но упрощает ликвидность,
исполнение, влияние заявки и маржинальную экономику. Его P&L нельзя переносить на реальный счёт
без моделирования spread, slippage, комиссий, налогов и задержек.

Заполнение market-заявки при обязательном закрытии в Sandbox не доказывает, что такая же заявка
исполнится по близкой цене в production. Production execution по-прежнему отсутствует.
